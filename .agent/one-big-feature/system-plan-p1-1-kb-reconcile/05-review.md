## Verdict: FAIL

The MMRAG_DIR/secrets fix in a7a2b2c is correct and matches the repo's established sourcing convention (finding 6, PASS). But a pre-existing bug in the reconcile-JSON parsing (present since e479beb, untouched by the a7a2b2c fix) means the ledger's `green` field will read `true` even when the nightly reconcile has real per-file failures — defeating the cron's own stated purpose ("silent failure on a KB cron is NOT acceptable," per the cron prompt in config.json). This must be fixed before the cron can be trusted.

(Note: a prior review pass of this same diff asserted "`green` correctly derives from captured status codes so a genuine failure would still show `green:false`" — that claim is false; see finding 1. Verified against `mmrag.py`'s actual output format, not assumed.)

## Findings

1. `orgs/clearworksai/agents/larry/bin/kb-reconcile-nightly.sh:27`: HIGH: `RECON_JSON=$(echo "$RECON_OUT" | grep -v "^SKIP" | tail -1 | grep -v "^$" || echo "{}")` silently discards the entire reconcile report. `mmrag.py`'s `_emit_report(report, json_out=True)` does `print(json.dumps(report, indent=2))` — a multi-line, pretty-printed dump, not a single-line JSON blob (verified: no `"SKIP"`-prefixed prints exist anywhere in `mmrag.py`, and simulating `tail -1` on an `indent=2` dump yields only the closing `}` character). `json.loads("}")` raises `JSONDecodeError` in the python heredoc, which is caught and silently falls back to `recon_data = {}` (kb-reconcile-nightly.sh:44-47). Every count field in the ledger row (`new_files`, `changed_files`, `failed_files`, `resumed_files`, `delete_failures.*`, etc.) is therefore always logged as `0`, regardless of the real reconcile outcome. Because `cmd_reconcile` in `mmrag.py` never calls `sys.exit()` on partial per-file failures (`failed_files > 0` / `delete_failures` are embedded in the report dict, not surfaced as a nonzero process exit — confirmed by reading `cmd_reconcile`, no `sys.exit` in that function), `RECON_STATUS` will typically still be `0` on a run with real failures — and the `green` computation (kb-reconcile-nightly.sh's python block) that's supposed to catch exactly this (`recon_stats["failed_files"] == 0 and recon_stats["delete_failures"]["files"] == 0 ...`) is checking permanently-zeroed fake data, not real counts. Net effect: the ledger will report `green: true` on nights with real reconcile failures, and the next night's cron check (`tail -1 ... kb-reconcile-ledger.jsonl`, config.json kb-reconcile-nightly prompt) will never alert Josh. Fix: don't slice the captured stdout at all — `mmrag.py reconcile --json --yes` only ever prints the one JSON document to stdout in `--json` mode, so pass `$RECON_OUT` to the python step unmodified (`json.loads(recon_json)` directly) instead of piping through `grep`/`tail`. If any stray non-JSON stdout lines are truly possible, parse via `json.JSONDecoder().raw_decode()` scanning for the first `{`, not `tail -1`.

2. `orgs/clearworksai/agents/larry/bin/kb-reconcile-nightly.sh:70`: LOW (pre-existing, not a regression): the wrapper's own process exit code is whatever the trailing `python3` heredoc's `sys.exit(recon_status)` returns — it never reflects `EDGES_STATUS`. Not exploited today because nothing consumes this script's exit code directly (the cron re-checks the ledger row, not the exit code), but if a future caller (systemd/launchd/monitoring) starts checking it, edge-extraction failures will be silently masked at the process-exit level. Fix: `exit $(( RECON_STATUS != 0 ? RECON_STATUS : EDGES_STATUS ))` or exit nonzero whenever the composed row isn't green.

3. `orgs/clearworksai/agents/larry/bin/kb-reconcile-nightly.sh:12`: LOW (matches existing convention in `bus/kb-query.sh` / `bus/kb-setup.sh`, not a regression): `[[ -f "$SECRETS_FILE" ]] && set -o allexport && source "$SECRETS_FILE" && set +o allexport` — if `source` fails partway (malformed `secrets.env`), the trailing `&& set +o allexport` is short-circuited and never runs, leaving allexport mode on for the rest of the script. Low impact here since no further un-exported locals are set after this line, but worth hardening (`; set +o allexport` unconditionally) fleet-wide including the two sibling scripts.

4. `orgs/clearworksai/agents/larry/bin/kb-reconcile-nightly.sh:18`,`22`: LOW: mmrag.py stderr is appended to `/tmp/kb-reconcile-nightly.err` with no rotation/truncation — grows unbounded across every nightly run, and `/tmp` is world-readable on a multi-user box. If a future mmrag.py traceback ever echoes an env var (e.g. a `GEMINI_API_KEY`-bearing request URL) to stderr, it lands in a world-readable file. Recommend moving the log under `$CTX_AGENT_DIR/state/` (or `/tmp` with `install -m 600`) and truncating/rotating it.
