Duplicate contact prevention Live — PR#317

Backfill scripts (calendar sync, comms sync) used to pass a slug-based --id to the contact writer. Any name variant — "Mark Lurie" vs "mark" vs "markmsiaorg" — minted a brand-new contact instead of matching the existing one. One real person had split into 3 separate CRM records.

Criteria — what changed

  • Backfills now call upsert-contact.py --match-email instead of --id <slug>.
  • find_contact_by_email() resolves the canonical contact by real email address, not by a generated slug.
  • Existing 3-way merges (already-split contacts) are not auto-resolved by this fix — they still sit in the approval queue for a human "yes."
What to expect: a new meeting/calendar invite from someone already in the CRM (under any name variant tied to the same email) updates their existing record instead of creating a lookalike duplicate. You should stop seeing 2-3 near-identical contacts for the same person going forward.

Meeting decisions & deal-state capture Live — PR#319

Every meeting run through the extractor already computed real decisions and a deal-state signal — it just threw them away after printing them to a log. This wires that output into the CRM's actual interaction record, without ever auto-flipping a sales pipeline stage from a guess.

Fireflies webhook fires
→
ff-extractor.py extracts decisions + deal_state
→
add-interaction.py folds them into the meeting's existing row
→
deal_state → pipeline stage ONLY if a deterministic keyword matches

Criteria

  • Decisions attach to the existing meeting interaction row (same source_ref) — never a duplicate row for the same meeting.
  • Re-running the same extraction is a true no-op if nothing changed (idempotent, proven against a live-data copy).
  • Deal-state text is never used to auto-flip a CRM sales stage unless it contains an explicit, deterministic keyword ("verbal yes," "signed," "went cold"). Anything else is preserved as text only, for a human to read and decide.

Commitment / owner capture (NEEDS-OWNER) Built once, real gaps found, repair in progress

The action-item extractor drops any commitment that doesn't have a clearly named, real-person owner — including first-person, vague-deadline ones like "it'll be a day or so, but I'm going to analyze the interviews and send them." That's the exact case a live audit caught disappearing. A fix was built tonight; independent re-verification found it doesn't yet handle the actual audit case correctly.

Intended criteria (target design, not yet fully working)

  • A commitment with a concrete due-date/timeframe and explicit commitment language ("I'll," "I'm going to") but a generic/self-referential owner ("I," "we") should be captured with owner: NEEDS-OWNER instead of silently dropped.
  • Items that also fail the due-date or explicit-language checks should still drop — this isn't a loosening of the bar generally, just closing one specific hole.
What the fixed output should look like (target, not yet verified live)
{
  "owner": "NEEDS-OWNER",
  "action": "analyze the interviews and send them to Dana and Mark",
  "due": "a day or so",
  "source_quote": "it'll be a day or so, but I'm going to analyze the
    interviews and send them both emails with Mark on copy"
}
What to expect right now: don't rely on this yet for vague first-person commitments — the independent re-check found real misses ("I'm going to…" still gets dropped in some cases, "a day or so" gets rejected as too vague). A repair branch (codex/fr001-owner-filter) is actively working the fix. Check back before trusting this specific case.

Client-file history preservation across rebuilds Built once, real gaps found, repair in progress

A nightly-style script rebuilds every knowledge/clients/*.md file from scratch off CRM data. Left alone, that rebuild would delete-and-regenerate the whole file every run — silently wiping any meeting-appended History or Open Items row the new decision-capture work writes in. A merge-preserving fix was built; independent re-verification found real edge cases still open.

Intended criteria (target design)

  • History rows and Open Items rows already present in a client file, that the fresh CRM-driven rebuild wouldn't reproduce on its own, get merged back in — not dropped.
  • Rows are de-duplicated and re-sorted by date, newest first.
  • Fields the rebuild is meant to own (CRM-sourced current-state fields) are untouched — this only protects meeting-appended content, not overrides CRM data.
What to expect right now: stale CRM rows can still survive incorrectly in some cases, and a row can detach from its meeting parent when multiple meetings get merged in the same pass — both confirmed by independent testing. Not yet safe to fully trust for multi-meeting weeks. Repair branch: codex/fr002-history-merge.

Records administrator — human-gated CRM change management Doc fixed, runtime policy not yet reconciled

A skill for keeping CRM and knowledge-base records in sync (stale-record resolution, orphan detection, duplicate merges) with a hard rule: nothing writes to a live record without an explicit human "yes." The written policy had an internal contradiction tonight (one section said "never auto-apply," another said "auto-apply STALE/MISSING automatically") — that's fixed. The live scripts still don't fully match the fixed policy yet.

Criteria (as documented now)

CaseRule
STALE (one side older)Present the exact diff + which timestamp wins. Wait for one batch "yes." Nothing writes before that.
MISSING (exists one side only)Propose the create as a change-list. Same batch-approval gate.
DUPLICATE / ORPHAN (merges, deletes)Individual human click per record — no batch "yes to all." A wrong merge or delete destroys history; a wrong update is fixable.
What to expect: once fully wired, you'll see a change-list surfaced for review (never a silent write) whenever a record looks stale or a duplicate/orphan is found. Right now the actual records-admin-sweep cron isn't registered live, so treat this as documented-but-not-yet-operating.

How the knowledge is organized — and kept clean

Four stores, each with one job. Nothing is duplicated across them on purpose — each fact lives in exactly one place, and other files reference it rather than copy it.

1. knowledge/clients/[client].md — the dossier

One markdown file per client. Human-readable narrative: contacts, current state, what's being delivered, financials, dated history, open items table. This is what you'd read cold to get oriented on a client in 60 seconds.

2. knowledge/meetings/[date]-[client]-[topic].md — the record

One file per meeting, permanent. Raw-ish: what was discussed, decisions, next steps. The dossier's History section links back to these rather than re-narrating them.

3. interactions.jsonl — the structured log

Machine-readable, append-mostly, one row per contact-touching event (meeting, email, call). This is what code reads — decisions, sentiment, commitments, dedup keys. The dossier is generated from this, not the other way around.

4. pipeline.json — the deal-stage source of truth

The only place a sales stage lives. Every stage change is written through upsert-engagement.py, which appends an audit trail (stage_history) and no-ops if nothing actually changed — so it can never silently drift or double-log.

What "kept clean" actually means, mechanically

  • One writer per store. add-interaction.py is the only thing that writes interactions; upsert-engagement.py is the only thing that changes a pipeline stage. Nothing hand-edits these files directly — that's an explicit rule, not a convention.
  • Idempotent by construction. Every writer dedups on a natural key (usually source_ref + contact_id) so re-running the same extraction twice never creates a duplicate row.
  • Dossiers are generated, not authored. knowledge/clients/*.md is rebuilt from CRM data on a schedule — so it can't silently drift from the structured truth, but (per the in-repair item above) that same rebuild is exactly what needs the merge-preserve fix so it doesn't erase meeting-appended content in the process.
  • No silent stage flips. Deal-state changes require a deterministic keyword match — an LLM's paraphrase of a conversation never moves money-relevant state on its own.

What to actually do with this

After a meeting

  • Check the client's dossier (knowledge/clients/[client].md) History section, or the raw interactions.jsonl row, for a decisions list — that's now durable, not just a Fireflies transcript you'd have to re-read.
  • If a commitment shows owner: NEEDS-OWNER (once FR-001 lands), that's a flag for you to assign a real owner — don't assume it's being tracked automatically.
  • Don't expect a sales-stage change to happen on its own from a meeting note — check pipeline.json/the dossier's "Deal stage" line yourself if the conversation sounded like it moved something.

When something looks off

  • Two similar-looking contacts for the same person → should be rarer now (PR#317), but existing ones from before the fix are still sitting in the approval queue waiting on your explicit merge decision.
  • A change to a CRM record you didn't make → check for a pending records-administrator change-list before assuming something auto-applied; per policy nothing should write without your "yes" (once fully wired).

Status to re-check before relying on it

  • FR-001 (commitment NEEDS-OWNER) and FR-002 (history preservation) — both have known real bugs, repair branches active. Ask for a status check before trusting the vague-commitment or multi-meeting-merge cases specifically.
  • records-administrator's live cron isn't registered yet — the policy document is right, the running system doesn't match it yet.
