Meeting chain — the call memory

Fireflies or pasted notes feed Meeting Intelligence. A real Fireflies webhook delivery is verified. The intended chain extracts outcomes, action items, decisions, and deal-state; files the meeting; updates a client’s dated history/open-items table; and emits only transcript-supported graph records. Current follow-through work is restoring its post-extraction write path.

Filter rule: casual future-tense self-disclosure such as “I’ll be learning more about coding in the next few weeks” stays context/no task. Only a concrete commitment or decision with a resolvable owner and usable time signal becomes work.

How knowledge stays clean

Rule: every useful fact needs a source, a canonical home, and a lifecycle. A summary without those is disposable context—not organizational memory.

Canonical home

Outputs route by content type: meetings, client records, briefs, proposals, and CRM interactions live in predictable locations.

Test: can a future agent find it without knowing who wrote it?

Provenance

Records keep their transcript ID, source file, CRM reference, or job key. Graph edges carry supporting context.

Test: can we trace the claim to dated evidence?

Explicit uncertainty

Unknown ownership/timing is preserved as NEEDS-OWNER / NEEDS-DEADLINE.

Test: did automation avoid inventing an obligation?

Reconciliation

Rebuilds preserve meeting-appended History/Open Items; maintenance checks duplicates, stale rows, and retrieval health.

Test: may a derived view rebuild without erasing human history?

Approval boundary

Executable work routes to bus/Multica; human decisions route to approval. Records work produces a change-list, not invisible edits.

Test: can a reviewer see what changed and why?

Observable no-output

Zero-yield meeting extraction records whether it was empty, casual, unextracted, or refined out.

Test: is “nothing happened” an auditable result?

What “clean” means

  • The transcript links to this update.
  • The action table drives recap bullets.
  • Closed rows are dated, not deleted.
  • Unresolved owner remains visible and inert.
  • Rebuilds preserve meeting-derived material.
  • Retrieval uses canonical paths plus provenance.

Mission Control v2 — the operating surface

Built and present: PR #287

The dashboard’s Mission Control page best-effort syncs local state, then serves a force-dynamic snapshot through /api/mission-control. It contains five KPIs (active engagements, shipped this week, on-time rate, open items, response time), active signals, client engagements, approval lane, activity, and fleet operations.

It is designed to answer: Which client is at risk? What is blocked? What needs my decision? What did the system observe?

Important limitation

Its data can be stale if upstream Multica sync is stale or its live feeds are down. The UI is a useful operational view, not proof that an external system accepted a change.

How to remember to use it

After calls

“Process my latest call.”
Or: “File this meeting for [client].”

For follow-through

“What is still open with [client]?”
Or: “Draft the follow-up from this meeting.”

For operations

“Show delivery status and decisions needed.”
Or: “Run the weekly review.”

The one habit worth keeping

After every meaningful conversation, give the system the transcript or notes. Thirty seconds of capture buys a dated record, client-history update, named work, exception list, and a durable answer to “what did we agree?”
